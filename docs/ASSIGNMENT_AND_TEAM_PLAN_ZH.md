## 2. 本周共同目标

项目定位：**视觉与触觉辅助的机械臂灵巧手工作台整理**。
先补齐公共数据集随机对象基线，再用触觉对照和具体工具任务体现技术深度。
R29 是复用 seed 3414、带已验证接近前缀的单案例；不能只改 seed 或重播同一轨迹就宣称随机抓取完成。
已有工具夹具实验不能替代公共数据集随机选物、抓姿生成和随机试验。

所有人先按仓库 README 建立自己的环境和分支。物理主要在 CPU 上运行，GPU 用于图像渲染，
无需把 3070、4060、3080 连接为多卡训练集群。各机一次先运行一个案例，测耗时和内存，再决定批量规模。
Windows 不设置 Linux 的 `MUJOCO_GL=egl`；本周无需 CUDA、PyTorch、VLM 或 VLA。

## 3. 组员 A：公共物体随机基线

分支建议：`workA/public-ycb-benchmark`。这是最高优先级任务，与 lead 共同完成。

**工作：**验证公共 YCB 罐子、肉罐和饼干盒的资产与参数；实现保存随机对象身份、初始位姿和种子的调度清单。
Lead 负责将控制器接到每回合重新感知、生成抓姿和接近的接口，A 负责调度、评价和故障复现。
这一接口完成前，A 可以检查旧基线、验证资产和准备评价器，不能声称 R29 已支持随机对象。

**数量：**先做 3 种物体 × 5 个随机位姿，共 15 个开发试验；配置冻结后，再做每物体 10 个独立位姿，共 30 个正式试验。
采用按物体分层的随机顺序，并保存选择/位姿 seeds。开发与正式 seeds 不重叠；正式批次中途不调参。
正式批次只启动一次；失败也计入 30 个计划试验，运行错误单独标记，保存原始失败后再说明是否补跑。

**交付：**协议 JSON、逐回合结果 CSV、真实轨迹/接触记录、每类至少一个成功或失败视频、失败分类和结果表。
验收需能从新进程重新执行“选物 → 摆放 → 抓姿生成 → 抓取/放置 → 评价”，并能按日志重算成功数和分母。
成功率可以低；不得删除失败或修改成功门槛来改善结果。硬件无关代码通过 PR 交给 lead。

现有历史批次入口可以先核对，但它不是 R29 随机化升级：

```powershell
.venv\Scripts\python.exe scripts\evaluate_public_ycb.py --help
```

## 4. 组员 B：触觉、灵巧动作与场景对照

分支建议：`workB/tactile-dexterity`。

**工作：**先复现已知工具整理和桌面支撑滚动，再回答“触觉是否帮助保持物体”“单指动作是否产生相对旋转”。
先做 1 个种子的成对试跑；通过记录检查后，固定协议做扳手 10 seeds × 触觉开/关，共 20 回合，
以及桌面滚动 5 seeds × 指关节动作开/关，共 10 回合。两组试验分开统计，不合并成功率。
下面 seeds 是计划占位，启动前与 A/lead 登记并确认未用于调参。

```powershell
.venv\Scripts\python.exe scripts\evaluate_v7_tool_feedback.py --tools tool_wrench --start-seed 5200 --count 10 --output results\B_tactile_5200
.venv\Scripts\python.exe scripts\run_v7_supported_rolling.py --start-seed 5300 --count 5 --video --output results\B_rolling_5300
```

**交付：**同种子成对结果、完整分母、最大通道力、掉落/碰撞、放置误差、相对旋转和腕部位移曲线，以及正反例视频。
验收关注真实物体相对手部运动，不能用腕部整体移动冒充灵巧操作；桌面支撑必须如实写明。
保留现有力和放置门限。可附一个挡板变化的探索案例，但不要扩大成未验证的避障成功率。
现有 OMPL 路线已验证环境为 Linux；Windows/WSL2 兼容性先单独检查，不作为本周主要交付的前置条件。

## 5. 组员 C：真人遥操作、Windows 复现与演示

分支建议：`workC/teleop-delivery`。

**工作：**从新 clone 安装并记录版本、安装问题和运行命令；本人操作虚拟机器人，录下目标选择、腕部移动、开合手指和停止。
不需要真实机器人。先做一个 60 秒以内的完整录制，保存视频和原始输入事件，再回放核验。

```powershell
.venv\Scripts\python.exe scripts\run_v7_workbench.py --view --seed 0 --duration 60 --output results\C_operator_take1
.venv\Scripts\python.exe scripts\run_v7_workbench.py --seed 0 --replay results\C_operator_take1\action_log.json --duration 60 --output results\C_replay_take1
.venv\Scripts\python.exe scripts\verify_v7_operator_recording.py --gui results\C_operator_take1 --replay results\C_replay_take1 --output results\C_recording_audit.json
```

**交付：**`workbench.mp4`、`operator_events.json`、`action_log.json`、`trace.json`、`events.json`、`metadata.json` 和审计输出，
并写明实际操作者及操作内容。核验工具不会替人证明身份；自动 GUI 测试不能称作真人记录。
工作台入口默认 `task_success=null`，不能因录像看起来合理改成抓取成功。
之后整理 3–5 分钟带介绍视频，包含应用、方法、量化结果、失败和限制；与 lead 协作完善报告图表和引用。
最后用新目录解压候选 ZIP，检查报告、视频、源码、运行依赖和所需数据均可取得。

## 6. Lead 与协作方式

Lead 使用 `lead/integration`，负责 fresh 感知/抓姿接口、控制器版本和评价门限，审核 A/B/C 的 PR、结果和失败记录，
统一报告技术主线及最终 ZIP。所有人都需要能解释自己提交的算法、实验和局限；报告据实写贡献与 AI 辅助。
当前仓库公开，组员可直接查看、clone 或 fork 后提交 PR；向原仓库直接推送仍需添加协作者。任务分配不等于已经发出邀请。

| 相对时间 | 里程碑 |
| --- | --- |
| D+1 | 三人完成新环境试跑，提交版本/设备/命令回执；lead 与 A 确认随机抓取接口缺口 |
| D+3 | A 完成 15 回合开发批次或明确接口阻塞；B 完成试跑，C 提交真人录制与回放结果 |
| D+5 | A 在接口通过后执行冻结的 30 回合；B 完成成对实验；每个失败均有名称与证据 |
| D+7 | 汇总报告/介绍视频/源码，另一成员新目录复现，lead 审核最终 ZIP |

若 A 的 fresh 抓姿接口未通过，先报告具体失败与日志，不开始“正式评测”也不自动扩展更多调参轮次。
这些是组内安排，不是老师截止日期；D 为团队确认启动之日。

代码、协议、结果摘要和图表可经 PR 合并；大视频和 raw 轨迹放在组内约定的 artifact 存储或 GitHub Release 资产中，
Git 只保存 `artifact_manifest.json`：文件名、相对路径/下载地址、字节数、SHA-256、产生它的 commit、seed 和命令。
每回合采用新的输出目录，禁止覆盖旧结果。先冻结 commit 和协议再运行，禁止直接从任意电脑的最新目录拼接成功率。
